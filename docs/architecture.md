# Phoenix Architecture

This is a map of Phoenix **as it exists right now** — not a history (see `docs/progress.md` for that) and not a decision log (see `docs/decisions.md`). If this document and the code disagree, the code wins; report the discrepancy rather than trusting either blindly.

---

## 1. Purpose

Phoenix is infrastructure for building and operating a controlled, quantitative trading ecosystem — not a single bot, and not (yet) a bot itself. It is being built as a set of small, independently-testable components: a frozen domain-contract core, an execution/read-side gateway to Bybit, and a documented set of not-yet-built future components (Reconciliation Engine, Market Regime Engine, Portfolio Orchestrator, Bot SDK, Dashboard).

This document makes no claim about the profitability or trading performance of any bot — that is out of scope for Phoenix's own architecture.

---

## 2. Architectural principles

Confirmed by code, tests, and `docs/decisions.md`:

- **Domain isolation** — domain contracts never import exchange-specific types. Verified by dedicated `TestPurityByAst`-style tests across the read-side (AST-walks the module's imports, asserts no `Bybit*`/`urllib`/`http`/`socket` names).
- **Ports/Adapters** — every capability is exposed as a `Protocol` (`@runtime_checkable`) Port, implemented by a Bybit-specific Adapter. See §4–6.
- **Explicit composition roots** — no component reads environment variables or constructs its own dependencies implicitly. Each capability has a `create_*` factory (pure construction), a `create_configured_*` factory (from a typed config object), and a `bootstrap_*_from_env` function (loads env → builds). Public one-call entry points (`query_bybit_demo_*`) sit on top.
- **Fail-closed** — when the read-side cannot confirm completeness of a remote answer (pagination cursor present, cardinality ≠ 1, symbol mismatch), it raises rather than returning a partial or best-guess result.
- **Observational vs actionable state** — the entire read-side only observes; it cannot create, cancel, or modify anything. Only `ExecutionGateway.execute()` writes.
- **Reproducibility of tests** — the full suite runs offline, no network access, using monkeypatched `urllib.request.urlopen` / dependency injection. No test hits real Bybit.
- **Deterministic testing + mutation testing** — every hito of consequence includes a manual mutation-testing pass against the real production file (mutate → run suite → confirm caught → restore → verify byte-identity).
- **Exchange boundary isolation** — the only place that constructs Bybit request bodies, parses Bybit response envelopes, or signs requests is within `execution_gateway`'s Bybit-specific adapters; nothing above that boundary knows Bybit's vocabulary (`retCode`, `Buy`/`Sell`, `orderLinkId`, etc.).

## 4. Execution write-side

**Port:** `ExecutionGateway` (`gateway.py`) — one method, `execute(request: ExecutionRequest) -> ExecutionResult`.
**Domain contracts:** `ExecutionRequest`/`ExecutionResult` (`contracts.py`) — `float`-based (not `Decimal`), frozen dataclasses, no Bybit vocabulary.
**Adapters (three, all implementing the same Port, interchangeable):**
- `BybitExecutionGateway` — translates to/from `BybitCreateOrderRequest`/`BybitCreateOrderResult` via `BybitDemoClient.place_order`, signs with HMAC, calls the private POST stack (`BybitRequestBuilder → HttpRequestExecutor → UrllibHttpTransport`, hardcoded to `POST`).
- `FakeExecutionGateway`, `DryRunExecutionGateway` — non-Bybit implementations for testing/dry runs.

**Error model:** business rejections (`BybitApiError`) translate to `ExecutionResult(status="rejected", ...)`. Infrastructure failures translate to `ExecutionInfrastructureError`, with the original exception preserved as `__cause__`. No `Bybit*` type crosses `execute()` (ADR-001/ADR-001A).

**Validated only by tests, never against real Bybit:** `UrllibHttpTransport.post()`, `BybitCreateOrderOperation`/`BybitCreateOrderPayloadBuilder`, real order-response interpretation, the full POST trading flow, cancellation. **No order has ever been created, filled, or cancelled against a real Bybit environment in this project's history.** Do not infer otherwise from the volume of test coverage.

## 5. Execution read-side

Five Ports, all `@runtime_checkable` `Protocol`s, all translating every failure to the same `ExecutionInfrastructureError` (no per-Port error hierarchy). Each has the same three-tier composition: `create_bybit_demo_*_reader` (pure) → `create_configured_bybit_demo_*_reader` (from `BybitDemoExecutionConfig`) → `bootstrap_*_reader_from_env` (loads env) → `query_bybit_demo_*` (one-call public function).

| Primitive | Port | Endpoint | Scope | Auth | Notes |
|---|---|---|---|---|---|
| Positions | `PositionsReader` | `GET /v5/position/list` | account-wide, `category=linear&settleCoin=USDT&limit=200` | private (HMAC) | No pagination — debt, capped at 200 positions. Hedge mode preserved via `(symbol, side)`, not `positionIdx`. Zero-size positions excluded. |
| Open Orders | `OpenOrdersReader` | `GET /v5/order/realtime` | account-wide, same scope, `limit=50` | private | Dual identity preserved (`exchange_order_id`/`order_id`). States: `new`/`partially_filled`/`untriggered`/`triggered`. |
| Wallet Balance | `WalletBalanceReader` | `GET /v5/account/wallet-balance` | account-wide, `accountType=UNIFIED` | private | No pagination (endpoint doesn't document any). Five account totals + per-currency balances in one snapshot. |
| Instrument Metadata | `InstrumentMetadataReader` | `GET /v5/market/instruments-info` | **per-symbol** (`symbol: str` param) | **public, unauthenticated** | Only primitive that isn't account-wide; only one using the public GET stack. Fail-closed on cardinality ≠ 1 and on symbol mismatch. |
| Exchange State Snapshot | `ExchangeStateReader` | *(aggregates the three account-wide above)* | account-wide | private (×3, independent) | See §6. |

Every primitive carries a remote `server_time_ms: int` sourced from Bybit's response envelope (`time` field), never a local clock. Every read is **exactly-once per call, no caching across calls on the same instance** — a behavioral guarantee, verified with spy-based tests, not just a design intent.

## 6. ExchangeStateSnapshot

`ExchangeStateSnapshot` (`exchange_state_contracts.py`), produced by `CompositeExchangeStateReader` through the `ExchangeStateReader` Port.

**What it aggregates:** exactly `positions` + `open_orders` + `wallet_balance` — the three account-wide, parameterless read-side primitives (Hitos 3.70–3.72).

**What it deliberately does NOT include:** Instrument Metadata (Hito 3.73). This was a decided architectural boundary, not an oversight — see §7.

**Non-atomicity, modeled explicitly, not hidden:** the three sub-reads are three independent HTTP GETs. `ExchangeStateSnapshot` has **no top-level `server_time_ms`** — a single "summary" timestamp would falsely imply one atomic instant. Instead:

- **`ObservationWindow`** (`earliest_remote_time_ms`, `latest_remote_time_ms`, `remote_time_span_ms`, all stored explicitly) is computed via `min()`/`max()` over the three sub-snapshots' remote `server_time_ms` — never `time.time()`, never a local clock.
- There is **no drift-tolerance field or policy**, deliberately. The snapshot *measures and exposes* drift; deciding what tolerance is acceptable is left to a future consumer (the not-yet-built Reconciliation Engine).
- `ExchangeStateSnapshot.__post_init__` cross-validates that its `observation_window` actually matches a fresh `min()`/`max()` recomputed from its own three sub-snapshots — rejects a window mixed in from a different round.

**Read order:** fixed, sequential — Positions → Open Orders → Wallet Balance. Documented as arbitrary-but-fixed, not a claim about temporal proximity. No concurrency (not demonstrated as necessary).

**Fail-closed on partial failure:** `query_exchange_state()` contains no `try`/`except` at all. Any sub-reader exception propagates unwrapped; readers after the failing one are never called. There is no partial-snapshot code path — either all three succeed and the snapshot is built complete, or nothing is returned.

**No-cache, exactly-once:** two calls to `query_exchange_state()` on the same `CompositeExchangeStateReader` instance issue six real HTTP calls (three per round), never reuse a prior result — verified with a two-round test using *smaller* timestamps in round 2, specifically to catch a "keep the historical max" bug.

**Configuration coherence:** the three sub-readers are built from the same `BybitDemoExecutionConfig` object (loaded once from environment), so they always authenticate with the same `api_key`/`api_secret`/`recv_window_ms`/`timeout_seconds`/base URL. This is now a behaviorally-tested property (`TestConfigCoherenceAcrossSubReaders`), not just an implementation detail.

**What this is:** a **base observational primitive** — the coherent set of remote facts Phoenix observed during one reading round, with enough temporal information for a future consumer to judge how close together those observations were.

**What this is NOT:** a Reconciliation Engine, a Risk Engine, a Repair Engine, or any trading policy. It does not compare observed state against expected/desired state, does not classify mismatches, does not decide what to do about drift, and cannot create, cancel, or modify anything.

## 7. Instrument Metadata boundary

Instrument Metadata is per-symbol (`query_instrument_metadata(*, symbol: str)`), while the other three read-side primitives are account-wide with no parameters. Combining a per-symbol primitive into an account-wide aggregate has no single obviously-correct answer — it requires a product decision about scope (all symbols? only symbols already seen in positions/orders? explicit symbol list?).

This was recognized as exactly this kind of ambiguity during Hito 3.74 and resolved by presenting three options to the user rather than choosing arbitrarily:
- **A** (chosen): `ExchangeStateSnapshot` excludes metadata entirely; it remains a fully independent primitive a caller invokes by symbol when needed.
- B (not chosen): an explicit `symbols` parameter on the aggregate.
- C (not chosen): automatic symbol derivation from observed positions/orders.

This is a decided boundary (ADR-002, Hito 3.74 update), not an open question — do not silently revisit it without a new explicit decision.

**What Instrument Metadata's fields represent (ADR-002, Decisión 6):** exchange-side constraints and capabilities for a symbol — price/quantity/leverage filters (`min_leverage`/`max_leverage`/`leverage_step`, min/max order quantity, tick size, min notional, etc.) describe what Bybit technically permits for that instrument. **They are not** recommended leverage, recommended position sizing, a risk policy, or capital allocation guidance — no code anywhere in this project treats them as such, and none should. A future Risk Engine or Order Validation layer may *consult* these as hard constraints; it must not be built on the assumption that they represent a recommendation.

## 8. Error boundaries

```
Remote / transport / response-parsing failure (any kind)
        │
        ▼
ExecutionInfrastructureError  (one shared domain exception, all Ports)
        │
        ▼
Domain-facing Port method (execute() / query_*())
```

- No per-Port exception hierarchy exists — `execute()` and all five `query_*` methods share the same `ExecutionInfrastructureError` for infrastructure failures.
- Business rejections are Port-specific: only the write-side has a concept of "rejected" (`ExecutionResult(status="rejected", ...)`) — a read has no equivalent, since there's no business decision to reject.
- Internal bugs (`TypeError`, `ValueError`, `AssertionError`, `RuntimeError`, `AttributeError`, `KeyError`) are never caught by a generic `except Exception` anywhere in the read-side or in `CompositeExchangeStateReader` — they propagate by identity, distinguishable from `ExecutionInfrastructureError`. This is a tested property (spy-based identity checks), not just an intent.
- The original exception is preserved as `__cause__` when Bybit-specific exceptions are translated to `ExecutionInfrastructureError` — never silently dropped.

## 9. Configuration and runtime

- **Environment:** Bybit Demo only (`D-011`). `Testnet` is excluded and rejected outright. `Mainnet` is not part of the current goal and must not be assumed or implemented by default — but `D-011` does not make this an eternal prohibition: it explicitly allows Mainnet *given a future explicit decision*. Do not build Mainnet support preemptively; do not treat the door as permanently closed either.
- **Deployment target:** Railway (`D-008`). As of the last recorded state, **no Railway service is connected to `main`** — `phoenix-smoke-demo` (the only service ever created) was manually deleted after Hito 3.68's real-world validation. `railway.toml` remains in the repo as reference config for a future manual redeploy, not an active service.
- **Region:** any future Bybit-connected Railway service must default to EU West / Amsterdam (`europe-west4`) — US regions are confirmed to fail, evidenced by one A/B test (not an exhaustive region survey).
- **`PYTHONPATH=/app/platform`** is a live, unresolved packaging debt (`D-014`, Decisión 2) — required as a manual Railway environment variable because `railway.toml`'s `buildCommand`/`pip install .` alone reproducibly fails to make `execution_gateway` importable at runtime on Railway's build image, for a cause that is suspected (Railpack layer assembly) but not confirmed. Do not assume this is resolved without checking `docs/decisions.md` D-014 again.
- No component reads environment variables at import time (`D-010`) — configuration is always injected explicitly at construction.

## 11. Known architectural debts

Active as of this document's last update — verify each against `docs/decisions.md` before relying on it, since debts get closed over time:

- **`PYTHONPATH=/app/platform` packaging workaround** (`D-014`, Decisión 2) — unresolved. `railway.toml` is not the complete source of truth for a live service's runtime.
- **Three independent private GET stacks per `ExchangeStateSnapshot` round** — each of Positions/Open Orders/Wallet Balance builds its own transport/sender/api instance from the same config, rather than sharing one. Confirmed (by adversarial audit, Hito 3.74 correction) to be a **performance/object-identity debt only** — configuration values are coherent across the three, this is not a correctness or coherence defect.
- **No pagination on Positions (`limit=200`) or Open Orders (`limit=50`)** — would silently lose data only above those thresholds in a single account; out of scope for current Demo usage.
- **`leverageFilter` non-`Mapping` tolerated as absence** in Instrument Metadata (accepted deuda MENOR, Hito 3.73) — a malformed-but-present block is treated the same as an absent one; only an individual malformed value *inside* a present block fails closed.
- **Env-loader raw `ValueError`** on structurally invalid timeout values, present since Hito 3.65 and replicated (not introduced) by Instrument Metadata's minimal loader (accepted deuda MENOR, Hito 3.73).
- **No Reconciliation Engine, no drift-tolerance policy, no expected-vs-actual comparison exists anywhere in this codebase.** `ExchangeStateSnapshot` measures and exposes observation drift; nothing in Phoenix currently decides what to do about it.
- **`BybitEndpoint.method` does not govern the HTTP verb on the main production path** (debt since the retrospective Auditoría C, recited in ADR-002 Decisión 2) — `bybit_url_builder.py`/`bybit_endpoint_executor.py`/`urllib_http_transport.py` (the productive POST stack) never read `.method`; the POST stack is hardcoded to POST and the GET stack is a separate, parallel primitive rather than a generalization that honors this field. The one place that *does* read `.method` is the standalone connectivity smoke test (`bybit_demo_connectivity_smoke_test.py`, see below) — a narrow, historical exception, not evidence the field is used productively. Not a bug — a known, accepted, unresolved debt.
- **The authenticated connectivity smoke test (built Hito 3.67, real-validated Hito 3.68) was never migrated to the reusable GET stack** built afterward (Hito 3.70's `HttpGetTransport`/`UrllibGetHttpTransport`) — `bybit_demo_connectivity_smoke_test.py` still uses its own original inline `urllib.request.Request(method="GET")`, documented from the start as an accepted one-off bypass. ADR-002, Decisión 2 records this as explicitly out of scope, not forgotten.
- **Test isolation / import identity stability** (found during the Hito 3.83 final re-audit, transversal to the whole suite, not caused by 3.83) — `pytest-randomly` is installed and randomizes test order on every run with no pinned seed. Under randomized order, a class of tests fails intermittently with `TypeError: scope must be ExpectedExecutionScope, got: ExpectedExecutionScope` (and the analogous `test_direct_import`/`test_same_identity_across_imports` pattern in `test_execution_gateway_bybit_endpoints.py`) — the same class loaded under two distinct module objects, so `isinstance` fails despite identical names. Confirmed by running both `0b24a2d` (pre-3.83-correction) and `76fef3d` (post) under identical seeds (1, 2, 3): the failing node-ID sets are byte-for-byte identical between the two trees, and zero failures ever land in `execution_ledger_event_contracts` tests — the flake is fully preexisting and causally unrelated to any hito through 3.83. The suite is green under deterministic order (`pytest -p no:randomly`) at every commit checked. Not fixed; worth a dedicated future hito given how much of this codebase's fail-closed philosophy rests on `isinstance` checks that a harness capable of producing duplicate class identities could, in principle, mask.

## 12. Next architectural boundary

A **Reconciliation Engine V1** now exists and is **accepted** (Hito 3.77, corrected after an independent adversarial audit and confirmed by a final independent adversarial re-audit — see §14) as the direction implied by `ExchangeStateSnapshot`'s design (observation without action, drift measured but not judged) and the explicit "future Reconciliation Engine" references throughout `docs/decisions.md`. V1 is deliberately narrow — **Detection & Classification only, explicitly no repair** — and is now a congealed accepted foundation, not a component under active development. Of the items previously listed here as undecided:

- ~~What "expected/desired state" means and where it comes from~~ — **resolved by Hito 3.76**: see §13, `ExpectedExecutionState`. Still undecided: how a real `ExpectedExecutionState` gets *populated* for a live account (a future projection engine).
- ~~Identity matching between observed and expected entities~~ — **resolved by Hito 3.77**: see §14. Positions by `(symbol, side)`; orders by Phoenix `order_id` only, identity-first/scope-second.
- ~~Mismatch classification~~ — **resolved by Hito 3.77**: eleven closed `Divergence` types, see §14.
- **A drift-tolerance policy** — still not decided. `ObservationWindow` is preserved in `ReconciliationResult` (§14) but V1 does not judge it.
- **Stale-round rejection rules** — still not decided; same reason.
- **Whether the engine (beyond V1) may also take repair actions** — still undecided. V1 itself contains zero repair-shaped code (verified by AST — no `cancel`/`repair`/`remediate`/`create_order`/`close_position`/`resize` as real identifiers), but that doesn't settle whether a future version will add it.
- **Account identity** — new item, carried over from ADR-004's MENOR-3: neither `ExpectedExecutionState` nor `ExchangeStateSnapshot` carries account identity; `reconcile_execution_state` presupposes (does not validate) that both inputs belong to the same account/configuration. Any fix must be symmetric and additive to both sides, not patched onto one.

**With V1 accepted, the next unit of work is design — not an implementation of repair.** No `RepairEngine`/`RepairPolicy` exists anywhere in this codebase, and none should be built until drift-tolerance/staleness, account identity, and the authority/boundaries of a future repair action are explicitly decided. Any repair design must also account for the documented coexistence of `OrderTypeMismatch` and `OrderPriceMismatch` on the same `order_id` (§14) — never act on an isolated `OrderPriceMismatch` without checking for a coexisting `OrderTypeMismatch` first.

**Hito 3.78 attempted to close the temporal asymmetry and deliberately stopped without writing code — `ARCHITECTURAL DECISION REQUIRED`, see ADR-006.** The observed side knows *when* it was observed (`ObservationWindow`, `server_time_ms`); the expected side still cannot say *since when* a given expectation holds authority. Forensic evidence showed the canonical reference cannot be chosen today without arbitrariness: `ExpectedExecutionState` has **no producer in production** (zero constructors under `platform/` — it is built only in tests); none of the seven candidate events is recorded anywhere (`ExecutionRequest`/`ExecutionResult` carry no timestamp; the remote ACK time is parsed into `BybitResponse.time_ms` but discarded by the create-order interpreter); the only domain clock (`MillisecondClock`) has exactly one consumer — the HMAC signature timestamp, a transport concern; and no `revision`/`sequence`/`event_id` concept, ledger, or persistence exists at all. ADR-006 records the reasoning that the coherent semantics would be **T7** (publication of a complete revision — the only candidate that is a fact *about the projection itself*, since all order-level events cannot date a multi-symbol projection), that **timestamp and version identity are distinct concepts**, and that any future provenance must be **immutable** — while implementing none of them.

**The chosen prerequisite is therefore the design of an Execution Ledger / projection engine.** Temporal provenance is not a field to bolt onto a contract; it is a property assigned by the authority that computes the projection. Once that authority exists, provenance follows from it (the ledger position/time the projection was derived from) instead of being hand-picked — and it shares that prerequisite with the account-identity gap.

**Hito 3.79 took up that design and hit a deeper blocker — `ARCHITECTURAL DECISION REQUIRED`, see ADR-007.** It did derive several non-negotiable requirements of the future ledger *from evidence rather than preference*: the ledger must record the submission attempt **before** the remote call (today a transport failure raises and records nothing, so the ambiguity of a lost response is not merely misrepresented but entirely lost — a duplicate-order hazard); a timeout may never be recorded as success or rejection; every fact must declare one of three distinct authorities (LOCAL / REMOTE / OBSERVED); the Phoenix `order_id` is a valid correlation and idempotency key, confirmed because it survives the round trip via `orderLinkId` and the gateway already verifies the correspondence on ACK; and Reconciliation V1 stays pure and never writes to the ledger. **But it stopped before freezing the event envelope**, because execution identity is not modelled anywhere: `account_id`/`user_id` have **zero occurrences across `platform/`**; `bot_id`/`trade_id`/`signal_id`/`event_id` exist only inside frozen `phoenix_core`, which `execution_gateway` never imports; the two contexts' order-id schemes are structurally incompatible (`phoenix_core` generates 42 characters, Bybit's `orderLinkId` limit is 36); and the account is implicit in the credentials. Resolving it touches `ExpectedExecutionState` and `ExchangeStateSnapshot` — both accepted and protected — so it is a cross-cutting decision, escalated rather than taken unilaterally.

**Hito 3.80 attacked both dependencies and closed one of them at the constraint level — `ARCHITECTURAL DECISION REQUIRED`, see ADR-008.** *Order identity:* the 42-vs-36 incompatibility is independently confirmed (`phoenix_core.ids.order_id()` is exactly 42 characters in 1000/1000 runs) and verified against Bybit's current official documentation, which also fixes the charset (`numbers, letters (upper and lower cases), dashes, and underscores`) and mandates uniqueness. The precise cause is **D-004's six-character semantic prefix, not UUID4** — a canonical UUID4 is exactly 36 and its `.hex` form is 32. Those constraints are now frozen (≤36, `[A-Za-z0-9_-]`, unique, **no truncation**, exact-string comparison), `phoenix_core` is not modified, and its `order_id` is ruled out for this role. *Account identity:* the problem changed shape. Bybit exposes an observable account identity — `userID`, `parentUid`, `isMaster` — via `GET /v5/user/query-api`, **the very endpoint the smoke test already calls** and the only path in this project ever validated against real Bybit (Hito 3.68); Phoenix currently discards those fields. So account identity **can be observed rather than invented**, which removes the "no authority exists" blocker that stopped 3.78 and 3.79. It is now settled that credentials authenticate but never identify (`api_key`, secret hashes, Railway variable names, `base_url` are all forbidden as canonical account identity), that environment and account are distinct dimensions, that the account-level/bot-level asymmetry is preserved (no `bot_id` on positions — the exchange cannot support that attribution), that per-bot order ownership lives in the ledger without the exchange knowing about bots, and that contracts receive identities rather than generating them. Two genuine decisions remain escalated: **where** the execution-context identity lives, and **who** generates the order id.

**Hito 3.81 closed both escalated decisions and implemented the identity foundations — ACCEPTED after a final independent adversarial audit, see §15.** `ExecutionAccountId` (internal, opaque, received rather than generated) and `ExecutionOrderId` (strict `ord_` + 32 lowercase hex canonical format, with an explicit generator) now exist, plus symmetric account-scoped wrappers around `ExpectedExecutionState`/`ExchangeStateSnapshot` and a thin cross-account-safe reconciliation layer — none of it touching the accepted contracts, all verified byte-identical. **The next unit of work is the Execution Ledger event model**, now unblocked in its identity dimension: the envelope, intent-vs-fact, LOCAL/REMOTE/OBSERVED authority per fact, uncertainty as a first-class state, event identity and deterministic ordering, append-only semantics, bot ownership as a ledger-only dimension (never embedded in `ExecutionOrderId`, never attributed to an aggregated remote position), replay, and the eventual Ledger → Projection Engine → `ExpectedExecutionState` revision relationship (which resumes ADR-006 once the authority it lacked exists). The Account Registry and `GET /v5/user/query-api` verification remain unbuilt and are not required to begin the Ledger's logical model, since `ExecutionAccountId` already functions as a valid internal identity on its own.

**Hito 3.82 designed the Execution Ledger event model and resolved most of it from direct evidence — `ARCHITECTURAL DECISION REQUIRED` on one dimension, see ADR-010.** Reconstructing the write-side flow boundary by boundary confirmed that on transport failure today **nothing at all is recorded** (deepens ADR-007 F7), and found four distinct code paths that already collapse into the same "outcome unknown" without leaving a trace. It closed a debt ADR-007/ADR-009 left open with direct evidence: the remote ACK time already has an established meaning — `BybitResponse.time_ms` is the exact same field already feeding `server_time_ms` in all four read-side interpreters, confirmed by reading the code, so capturing it for the ledger invents nothing. It derived without material ambiguity: three authorities (LOCAL/REMOTE/OBSERVED) as a property of the event *type* (same pattern as `Divergence`, ADR-005 Decision 7); intent and attempt collapsing into a single `OrderSubmissionAttempted` fact, since no evidence of a separate intent-formation moment exists; uncertainty as its own explicit fact (`OrderSubmissionOutcomeUnknown`), distinct from mere silence; `ExecutionAccountId` universal on the envelope vs. `ExecutionOrderId` scoped to the payload; the event's own identity as a local opaque type with no format frozen (no external boundary to cross, unlike `ExecutionOrderId`); ordering scoped logically per account, with the assignment mechanism deferred to a persistence layer that doesn't exist yet; revision reaffirmed as the Projection's responsibility, not the Ledger's; a four-field minimal envelope; five V1 event types, all order-scoped (no fills — no execution/trade read primitive exists; no cancel/amend — no such primitives exist); one frozen dataclass per event type under a non-instantiable marker (same pattern as `Divergence`); and zero new coupling with Reconciliation V1. **One dimension remains escalated: bot ownership** — neither its type/format nor whether attribution should be mandatory or optional on the intent-level fact is derivable from the repository; `architecture.md`'s own component map already anticipates a future Dashboard (typically human-triggered, not bot-triggered), which makes the question genuine rather than rhetorical. A recommendation is on record (mint an optional `ExecutionBotId`, structurally analogous to `ExecutionAccountId`) but not decided unilaterally.

**Hito 3.83 implemented ADR-010's contracts after the project director resolved both escalated blockers — ACCEPTED after a final independent adversarial re-audit, see §16.** The director chose Option A for bot ownership (2026-08-27): `ExecutionBotId` is optional, received rather than generated, structurally identical to `ExecutionAccountId`. A second, narrower blocker surfaced only while implementing `OrderObservedOpen` literally from ADR-010's text — whether V1 should accept orphan open orders (`order_id is None`) — and was resolved the same way (2026-08-29): V1 represents exclusively the correlated case; `execution_order_id` is mandatory; orphans remain observable only through Reconciliation V1's `UnattributedExchangeOpenOrder`; no sixth event type was added, an explicit debt for a later hito rather than a silent omission. With both resolved, all five V1 event types, the three authority markers, and the four-field envelope now exist as pure contracts, confirmed accepted — nothing in the write-side or read-side was touched, and nothing constructs these contracts yet.

**With 3.83 accepted, the next architectural boundary is Execution Ledger Writer / Durability design — not write-side integration.** Wiring `OrderSubmissionAttempted` into `bybit_gateway.py` before any real call would be premature: none of the following is decided, and guessing any of them would freeze an accident into the write path exactly as this project's STOP protocol exists to prevent.

1. Who generates `ExecutionLedgerEventId`, and where.
2. When it is generated — at construction, or at the moment of durable append.
3. What append-only storage technology persists the ledger (none exists today).
4. What "durable" concretely means for this project (fsync'd to local disk? acknowledged by a remote store? both?).
5. How to guarantee `OrderSubmissionAttempted` is durable **before** any remote transmission — the entire reason ADR-007 derived this ordering requirement in the first place.
6. What happens if persistence itself fails before the network call is even attempted.
7. What happens if `Attempted` persists but the process dies before transmitting — a lost-attempt window distinct from the transport-failure case `OrderSubmissionOutcomeUnknown` already models.
8. Physical ordering per `ExecutionAccountId` — `occurred_at_ms` explicitly does not guarantee total order (§16).
9. A `sequence` assignment mechanism — deliberately deferred out of the envelope in ADR-010 Decision 10, precisely until this is designed.
10. Idempotency of append (what happens on a retried write of the same fact).
11. Crash recovery — how a restarted process reconciles its own in-flight ledger state.
12. Replay — who consumes the ledger and in what order, especially relevant once a Projection Engine exists.
13. Atomicity between the local append and the remote transmission — two independent systems that cannot commit as one operation.
14. A stated strategy for the resulting dual-write problem, rather than an implicit best-effort.

None of these is answered by this document. They are listed here precisely so the next hito starts from "what must be decided" instead of "what seems reasonable to implement."

**Hito 3.84 took up exactly that list and designed the Writer/Durability boundary — `STOP: DECISIÓN REQUERIDA` on one dimension, see ADR-011 and §17.** Thirteen of the fourteen questions are now answered from evidence: durable is defined operationally (fsync'd commit on process-independent storage; memory/buffer/unsynced `write()` explicitly forbidden as "durable"); the Writer generates a UUID4 `ExecutionLedgerEventId` immediately before append — UUID7/ULID rejected precisely *because* their time-ordering would tempt misuse as a sequence; `sequence` is a per-account monotonic integer assigned inside the append transaction, with no cross-account order claimed; the append contract returns an `AppendReceipt` only after the durable commit returns; append idempotency is keyed on **content** (`account, order_id, event_type`) so a retry after a lost ACK returns the existing receipt instead of a duplicate row; the Attempted-before-network invariant is enforced by a Port-level wrapper that is the only thing holding the inner adapter; every transport failure yields `Unknown` fail-closed because the transport **empirically cannot** distinguish sent from not-sent (a response-timeout was shown to occur *after* the full order body and `orderLinkId` reached the remote socket); recovery never infers "not sent" from a missing terminal event and must query the read-side by `orderLinkId`; a post-remote append failure halts the account rather than flying blind; one logical writer per account; and the dual-write problem is handled as write-ahead log + idempotent remote key (`110072` = "prior attempt was accepted") + read-side recovery — not outbox, not saga, not pretended atomicity. **The one escalated question was the physical durability topology and its accepted loss profile** (SQLite on a Railway volume — recommended — versus managed PostgreSQL); **the project director resolved it toward managed PostgreSQL on 2026-09-11**, accepting the project's first third-party runtime dependency and a network hop inside the WAL path, with single-writer-per-account now a Phoenix-enforced invariant rather than a platform one. Not implemented. Three gaps surfaced that must be closed before any implementation: no V1 event can represent an order observed **closed** (so a MARKET order filled during a lost response cannot be reconciled in the ledger), the read primitive `orderLinkId` + `openOnly=1` does not exist, and `110072` is misclassified as generic infrastructure today.

## 13. Expected Execution State (Hito 3.76 — ACCEPTED)

Four immutable domain contracts in `expected_execution_state_contracts.py` — pure vocabulary, no Port, no HTTP, no I/O, no Reconciliation Engine, no wiring to `ExchangeStateSnapshot`.

**Exact string identity, no silent normalization — behaviorally tested.** `symbol` and `order_id` are never `strip()`/`upper()`/`lower()`'d anywhere in this module, consistent with the observed read-side (`bybit_positions_response_interpreter.py`/`bybit_open_orders_response_interpreter.py` don't normalize either). `"BTCUSDT"`, `"btcusdt"`, `" BTCUSDT "` are distinct values, preserved exactly, and scope containment/deduplication are case- and whitespace-sensitive (`TestExactStringIdentityNoNormalization`, added in the post-3.76 correction after an audit found this property held in production but was uncovered by tests).

**`ExpectedExecutionScope`** — `symbols: tuple[str, ...]`, no duplicates. Defines *where* the state is authoritative. A symbol outside `scope` is **unknown** (Phoenix asserts nothing) — never "expected flat." An empty scope (`symbols=()`) is valid, by the same precedent as every other collection field in the read-side (empty = legitimate, never an error).

**`ExpectedPosition`** — identity `(symbol, side)`. Fields: `symbol`, `side` (same `"buy"`/`"sell"` vocabulary as `ExecutionPosition`), `quantity` (`Decimal`, finite, `> 0`). Represents the *aggregated* position Phoenix expects for that instrument/side — deliberately without `entry_price`/`leverage`/`unrealized_pnl`/`liquidation_price`/`margin`/`positionIdx`/`bot_id`/`strategy_id`. A zero-quantity expected position is never represented: "flat" is authoritative scope + absence of the corresponding `ExpectedPosition`.

**`ExpectedOpenOrder`** — identity `order_id`, which is **Phoenix's own identity** (conceptually `orderLinkId`), never `exchange_order_id` — Phoenix cannot assert in advance what id the exchange will assign to an order that doesn't exist remotely yet. Fields: `order_id`, `symbol`, `side`, `order_type` (`"market"`/`"limit"`), `quantity` (`Decimal`, finite, `> 0`), `price` (`Decimal | None`, finite, `> 0` when present — **not** coupled to `order_type`, following `ExecutionOpenOrder`'s Hito 3.71 observational precedent rather than the write-side `ExecutionRequest`'s stricter coupling), `reduce_only` (strict `bool`). Deliberately without `exchange_order_id`/`filled_quantity`/`status`/`server_time`/`bot_id`/`strategy_id` — dynamic execution-progress fields are excluded so a future Reconciliation Engine can't confuse legitimate fill progress with divergence; their semantics are for that future hito, not this one.

**`ExpectedExecutionState`** — `scope` + `positions: tuple[ExpectedPosition, ...]` + `open_orders: tuple[ExpectedOpenOrder, ...]`. Invariants enforced in `__post_init__`: every position/order symbol must belong to `scope` (fail-closed — an out-of-scope expectation invalidates construction, never silently dropped); no duplicate `(symbol, side)` among positions; no duplicate `order_id` among orders (two economically-identical orders with different `order_id` **survive** — identity is `order_id` alone); `BUY`/`SELL` of the same symbol coexist (hedge, same principle as Positions Read). Empty `positions`/`open_orders` within a non-empty `scope` is valid and means *expected absence* — not "no opinion."

**Not implemented, on purpose:** no `ExpectedExecutionState.reconcile(snapshot)`, no `ExchangeStateSnapshot.compare(expected)` — verified by AST that the module doesn't import `ExchangeStateSnapshot` and contains no reconciliation vocabulary (`reconcile`/`MATCH`/`MISSING`/`UNEXPECTED`/`MISMATCH`/`repair`) as real code (only legitimate explanatory prose). No persistence, no Canonical Execution Ledger, no projection engine that populates a real `ExpectedExecutionState` from bots/intents — this hito defines the vocabulary only. See ADR-004 for the full architectural reasoning, including why the scope-empty and `price` decisions were resolved from precedent rather than by intuition.

**Two debts registered explicitly for the Reconciliation Engine hito, deliberately not resolved here:**
- **`price` semantics are under-specified.** `ExpectedOpenOrder` currently allows `order_type="limit"` with `price=None` and `order_type="market"` with `price>0` — deliberately, not by oversight (see ADR-004). This does **not** mean either combination is operationally meaningful. Before comparing `price` against `ExecutionOpenOrder`, the Reconciliation Engine must explicitly define the semantics of: `expected.price is None`, `observed.price is None`, a market order with an observed/expected price, and a limit order expected without a price.
- **No timestamp/freshness on `ExpectedExecutionState`, and no account identity on either `ExpectedExecutionState` or `ExchangeStateSnapshot`.** Both are acceptable today (no ledger/projection engine exists to populate a real timestamp; nothing yet compares two accounts against each other), but both need a decision before/during the Reconciliation Engine hito — the account-identity gap in particular must be closed **symmetrically and additively on both sides**, not patched onto `ExpectedExecutionState` alone.

**Status of those two debts as of Hito 3.78:** the `price` debt was **closed by Hito 3.77** (see §14, `price` semantics V1). The timestamp debt was taken up by **Hito 3.78 and found to be blocked, not solvable by adding a field** — the parenthetical above ("no ledger/projection engine exists to populate a real timestamp"), written during 3.76, turned out to be the whole answer: see ADR-006. Account identity remains open and shares the same prerequisite. Neither is resolved yet, and neither should be patched onto one side alone.

## 14. Reconciliation Engine V1 (Hito 3.77 — ACCEPTED)

`reconcile_execution_state(*, expected: ExpectedExecutionState, observed: ExchangeStateSnapshot) -> ReconciliationResult` — a pure module function in `reconciliation_engine.py`, not a Port, no I/O. **Accepted and stable** — treat this as the current public contract; see `docs/progress.md` for the full acceptance chain. An independent adversarial audit classified `CORREGIR HITO 3.77` (two IMPORTANTE findings, one MENOR); the correction described below closed all three, and a final independent adversarial re-audit (own probe harness, own reinjected mutations, a 4000-trial randomized invariant search, zero violations) confirmed `ACEPTAR HITO 3.77`. Detection & Classification only — it is a congealed accepted foundation, not a component under active development; see §12 for what is deliberately not decided yet.

**Scope: Detection & Classification only.** No repair, no cancellation, no order creation, no position closing, no SL/TP/leverage/margin changes, no sizing, no capital allocation, no persistence, no ledger. Verified by AST that the module contains none of `cancel`/`repair`/`remediate`/`create_order`/`close_position`/`resize` as real code (class/function/attribute names) — only as legitimate explanatory prose is any of that vocabulary permitted.

**Purity.** Same style as the rest of `execution_gateway`: `reconciliation_engine.py` imports only `exchange_state_contracts`, `expected_execution_state_contracts`, `reconciliation_contracts`, `reconciliation_precondition_error` — zero Bybit/HTTP/urllib/os/Railway. Same inputs always produce the same `ReconciliationResult`, including divergence order — no local clock, no network, no environment reads, no mutable global state.

**Position identity: `(symbol, side)`, matched only within `expected.scope`.** Same principle as `ExpectedPosition`/`ExecutionPosition`. A position observed outside `expected.scope.symbols` is never classified `UnexpectedExchangePosition` — Phoenix has no authority to assert anything about it. String identity is exact — no `strip()`/`upper()`/`lower()` anywhere in matching.

**Order identity: Phoenix `order_id` only — `exchange_order_id` never participates in matching, not even as a fallback.** `ExpectedOpenOrder.order_id` matches exclusively against `ExecutionOpenOrder.order_id`. An orphan order (`order_id is None`) whose `exchange_order_id` happens to coincide with some expected order's Phoenix `order_id` must never be treated as matched — verified with a dedicated mutation and test.

**Identity-first, scope-second — the central rule for orders.** Order matching runs in two strictly sequential phases:
1. Walk `expected.open_orders`, look up each `order_id` among observed orders — **scope does not participate here**. A matched order can produce multiple field-level divergences (including `OrderSymbolMismatch` if the observed symbol falls outside `expected.scope`) without ever being reclassified as missing/unexpected — identity matching already established it's the same entity.
2. Walk the observed orders **not** matched in phase 1 — only here does scope decide whether to report as unexpected/unattributed or ignore.

Four required scenarios, each with a dedicated test and independent mutation coverage: a matched order whose observed symbol falls outside scope still produces `OrderSymbolMismatch` (never ignored, never split into missing+unexpected); an unmatched order outside scope is ignored; an orphan outside scope is ignored; an orphan inside scope becomes `UnattributedExchangeOpenOrder`.

**Orphan orders (`order_id is None`).** An observed order without Phoenix identity (`exchange_order_id` always present) is classified `UnattributedExchangeOpenOrder` if its symbol is within `expected.scope`, or ignored otherwise. No `order_id` is ever invented; `exchange_order_id` is never substituted as Phoenix identity.

**Duplicate observed identities — rejected fail-closed, as a precondition of the engine itself (post-3.77 correction).** Neither `PositionsSnapshot` (Hito 3.70) nor `OpenOrdersSnapshot` (Hito 3.71) — both accepted, protected contracts — guarantee uniqueness of `(symbol, side)` or Phoenix `order_id` respectively among their entries. An independent adversarial audit demonstrated that the original matching-by-dictionary implementation silently dropped a real, distinct observed entity when its identity was repeated, and could even yield `is_in_sync=True` while an unaccounted-for order or position existed. Because the observed contracts are protected and were not modified, the guarantee was built as two new preconditions inside `reconciliation_engine.py` itself, run before any matching: `_reject_duplicate_observed_position_identities` and `_reject_duplicate_observed_order_ids`, both raising `ReconciliationPreconditionError` on the first duplicate found (deterministic, contractual-order traversal). The check runs over the **entire** observed snapshot, including identities outside `expected.scope` — scope decides economic authority over what gets reported, not whether the observed snapshot itself is structurally valid; a duplicate outside scope still fails closed. Orphan orders (`order_id is None`) are explicitly exempt from this check — two orphans never collapse into a "duplicate," since `None` is not a Phoenix identity; each remains distinct, identifiable only by its own `exchange_order_id`. Identity comparison in duplicate detection is exact-string, matching every other identity comparison in this component — no normalization was introduced.

**Eleven divergence types, no free strings.** `Divergence` is a non-instantiable marker base class; eleven concrete `frozen` dataclasses subclass it — three for positions (`MissingExpectedPosition`, `UnexpectedExchangePosition`, `PositionQuantityMismatch`), eight for orders (`MissingExpectedOpenOrder`, `UnexpectedExchangeOpenOrder`, `UnattributedExchangeOpenOrder`, `OrderSymbolMismatch`, `OrderSideMismatch`, `OrderQuantityMismatch`, `OrderTypeMismatch`, `OrderPriceMismatch`). Classification is the Python type itself (`isinstance`), never a free string or generic `Literal` tag. There is no `PositionSymbolMismatch`/`PositionSideMismatch` — a position's identity **is** `(symbol, side)`, so once matched it can only diverge on `quantity`.

**`ReconciliationResult`: `is_in_sync` is a `@property`, never a second field.** `divergences: tuple[Divergence, ...]` is the sole source of truth; `is_in_sync` is derived on every access (`len(divergences) == 0`) — no stored boolean that could, through a construction bug, contradict the actual divergence list. `observation_window` is preserved verbatim from the observed `ExchangeStateSnapshot` — the caller knows which window produced these divergences, but V1 makes no freshness/staleness judgment.

**`price` semantics V1 — closes ADR-004's MENOR-1.** A `ReconciliationPreconditionError` (pure domain exception, not infrastructure — this component does no I/O) aborts, before any matching, if any expected `order_type="limit"` has `price=None` — fail-closed, `None` is never interpreted as "no opinion" or zero. For an expected `market` order, price is **not** part of the V1-reconcilable expectation — `OrderPriceMismatch` is never emitted for a `market`-expected order on price grounds alone, even if `expected.price` happens to be populated (permissive semantics inherited from 3.76, left untouched) or the observed price differs. For a matched `limit` order, comparison against `observed.price` is exact (including `observed.price is None` → `OrderPriceMismatch`). The gate is always `expected.order_type`, never `observed.order_type` — a type mismatch between the two is already reported separately as `OrderTypeMismatch`.

**`OrderTypeMismatch` and `OrderPriceMismatch` may coexist for the same `order_id` (documented, unchanged behavior — post-3.77 correction).** Because the price gate is `expected.order_type` and never `observed.order_type`, a matched order whose `expected.order_type == "limit"` but whose `observed.order_type` differs can produce both divergences at once — they are two separate facts about the same order, and neither invalidates the other. This was already the implemented behavior when 3.77 first shipped; an independent audit judged it defensible and it is left unchanged here, but it was a semantic decision made without triggering the mandatory STOP-and-present-options protocol for genuine ambiguities — that lapse is registered honestly in `docs/decisions.md` (Corrección post-3.77) rather than silently fixed or hidden. **A future repair policy must not act on an isolated `OrderPriceMismatch` without also checking for a coexisting `OrderTypeMismatch` on the same `order_id`** — the observed order may not even be of the expected type, and "repairing the price" of a wrong-type order is not economically meaningful.

**`ObservationWindow` propagation — behaviorally covered (post-3.77 correction).** Production already propagated `observed.observation_window` into `ReconciliationResult.observation_window` by object identity (`is`), but no test exercised this through the public `reconcile_execution_state()` entry point — every prior test constructed `ReconciliationResult` directly. Dedicated tests now verify object identity, a non-trivial earliest/latest/span, and non-reconstruction from zero; the independently-reinjected mutant that reconstructs the window is confirmed detected.

**Partial fills: `expected.quantity` vs `observed.quantity`, never `remaining`.** A legitimate partial fill (`observed.filled_quantity > 0`) is never, by itself, a divergence — `OrderQuantityMismatch` always compares `expected.quantity` against `observed.quantity` (the order's original size), never `observed.quantity - observed.filled_quantity`. Observed `status` never produces a divergence on its own in V1.

**No freshness policy, no account identity — both explicitly presupposed, not validated.** `reconcile_execution_state` assumes `expected` and `observed` belong to the same account/configuration; it cannot validate this (neither contract carries account identity yet — ADR-004's MENOR-3, still open). `ObservationWindow` is carried through for the caller's benefit, but V1 does not decide what counts as "too old."

**Determinism.** `set`/`dict` are used exclusively as internal lookup structures (scope membership, identity indexing) — never as a source of output ordering. Divergence order: (1) `expected.positions` in contractual order, (2) `observed.positions.positions` in contractual order for the unmatched remainder, (3) `expected.open_orders` in contractual order (missing, or matched with mismatches in the fixed field order symbol→side→quantity→order_type→price), (4) `observed.open_orders.orders` in contractual order for the unmatched remainder.

**Mutation battery: 24 specified, 24 detected, 0 equivalent (corrected — post-3.77 correction).** The original implementer's report claimed "23/24 detected, 1 confirmed equivalent" for M9 ("a matched order with symbol outside scope is ignored"), reasoning that `ExpectedExecutionState.__post_init__` already structurally rejects any `ExpectedOpenOrder.symbol` outside its own `scope`. That reasoning is correct, but only because the implementer's M9 mutated `order.symbol` — the **expected** side's symbol, which is indeed structurally guaranteed in-scope. An independent audit built the correct M9 mutation against `observed_order.symbol` — the **observed** side, which can legitimately fall outside scope even after a successful `order_id` match (exactly the scenario `OrderSymbolMismatch` exists for) — and confirmed it **is** detected by the existing `TestIdentityFirstScopeSecond` tests. There are no equivalent mutants in the original battery.

**Duplicate-observed-identity mutation battery (N1-N12, post-3.77 correction): 12 specified, 12 detected, 0 equivalent.** Covers: precondition removal with last-wins and first-wins dict semantics, for both positions and orders (N1-N4); a duplicate order_id outside scope silently ignored instead of failing closed (N5); two `order_id=None` orders wrongly treated as a Phoenix duplicate (N6); two distinct orphans collapsed into one `UnattributedExchangeOpenOrder` (N7); case/whitespace-normalized duplicate detection for order_id and position symbol (N8-N9); `ObservationWindow` reconstructed with shifted values, replaced by fixed constants, and replaced by a value-equal-but-distinct instance (N10-N12) — the last of these is detected only by the object-identity (`is`) assertions and correctly left undetected by pure-value assertions, confirming the two are not redundant.

## 15. Execution Identity Foundations (Hito 3.81 — ACCEPTED)

Three identity value objects plus two account-scoped wrappers, added to close the two decisions ADR-008 escalated. **Accepted and stable** — treat this as the current public contract; a final independent adversarial audit (own probe harness, 74/74 passing; own reinjected mutation battery M1-M20 plus 15 additional mutations, 34/35 detected and 1 confirmed equivalent by unreachable-branch proof; Bybit's `orderLinkId` constraints re-verified against current official documentation) confirmed `ACEPTAR HITO 3.81` with zero findings — see `docs/progress.md` for the full acceptance chain. It is a congealed accepted foundation, not a component under active development; the next unit of work is the Execution Ledger event model (see §12), not further changes here. Nothing here flows through the write-side or read-side yet — `ExecutionRequest`, `ExpectedOpenOrder` and `ExecutionOpenOrder` all keep `order_id: str` unchanged.

**`ExecutionAccountId` — Phoenix's internal, opaque account identity.** A frozen single-field value object that **receives** an identity; it never generates one. Literal exact preservation, no `strip`/`upper`/`lower`: `"ACCOUNT-A"`, `"account-a"` and `" ACCOUNT-A "` are three distinct accounts. Credentials authenticate but never identify — deriving this from `api_key`, a secret's fingerprint, an environment variable name, `"BYBIT_DEMO"` or a `base_url` is forbidden. Deliberately **no canonical text format and no official generator are frozen**, because the authority that would mint them (a future Account Registry) does not exist; the contract can carry any received identity without that freezing its shape.

**`ExchangeAccountIdentity` — the exchange's observable account identity, as vocabulary only.** Frozen; `exchange`, `environment` and `remote_user_id` are **all three identity**, not metadata: Demo and Mainnet are separate Bybit systems, so `(bybit, demo, 123)` and `(bybit, mainnet, 123)` are different accounts. `remote_user_id` is a `str`, not an `int` — Bybit exposes both `userID` (integer) and `userIDInt64` (string), and this bounded context already preserves remote identifiers as exact strings (cf. `exchange_order_id`); an `int` is rejected. No `parent_uid`/`is_master` (they describe main/sub-account hierarchy, not this account's identity) and no credentials of any kind. **No production component constructs this yet** — the primitive that would observe it from `GET /v5/user/query-api` does not exist, and the smoke test was not modified.

**`ExecutionOrderId` — Phoenix's execution-order identity, strict canonical format.** `ord_` + exactly 32 **lowercase** hex characters = 36, the maximum Bybit's `orderLinkId` accepts. The contract validates the full official format, not mere boundary compatibility: a string that merely *fits* — short enough, valid charset — is rejected. Two consequences are deliberate: a canonical dashed UUID4 (36 chars, valid charset) is rejected, and so is the 42-character `phoenix_core` legacy format. Lowercase is strict because `uuid4().hex` produces lowercase and Bybit's documentation does not address `orderLinkId` case sensitivity — accepting uppercase would create two distinct strings claiming to be the same order without evidence the exchange agrees. It never embeds `bot_id`, `account_id` or `strategy_id`.

**`create_execution_order_id()` — the explicit, authorized generator.** Lives in its own module (`*_factory.py` / `create_*`, the repo convention), never inside `__post_init__` or a `default_factory` — a contract that mints its own identity cannot represent an identity that already exists, such as one read back from the exchange. It preserves UUID4's 122 effective random bits intact: **no truncation, no trimming, no character removal**. Collision safety is documented as **probabilistic, never a mathematical impossibility** — Phoenix keeps no global registry of issued identities, and a collision would be rejected by Bybit (which requires `orderLinkId` uniqueness) rather than detected locally.

**`phoenix_core` is untouched and byte-identical.** Its `order_id()` produces 42 characters and therefore cannot cross the `orderLinkId` boundary. It remains a legitimate *internal* identity of that bounded context; it is simply not the execution bounded context's canonical identity. It is not truncated, not transformed, not used as generator input, and `execution_gateway` does not import `phoenix_core` at all (verified by AST in tests). It is **not** declared globally deprecated — the repository has taken no such decision.

**Account-scoped wrappers — they wrap, they never rewrite.** `AccountScopedExpectedExecutionState` and `AccountScopedExchangeStateSnapshot` each hold an `ExecutionAccountId` plus the real accepted contract. `ExpectedExecutionState` (Hito 3.76) and `ExchangeStateSnapshot` (Hito 3.74) were **not modified** and remain byte-identical; the wrappers copy no inner fields, reconstruct no `ObservationWindow`, and preserve the wrapped object **by object identity** (`is`). They carry only `ExecutionAccountId`, not `ExchangeAccountIdentity`: the guarantee these wrappers exist to provide — never comparing one account's expectation against another's observation — is fully obtained from the internal identity. Verifying that an internal identity really corresponds to a given remote account is *binding verification*, and belongs to the Account Registry that does not exist. They remain account-level: no `bot_id`.

**`reconcile_account_scoped_execution_state()` — a thin layer that delegates.** It checks types, compares `ExecutionAccountId` by exact equality, **fails closed** with `CrossAccountReconciliationError` when they differ, and otherwise delegates to `reconcile_execution_state`, returning **exactly** the object the accepted reconciler produced. It reimplements nothing: no position or order matching, no scope filtering, no price comparison, no duplicate detection — a guarantee protected behaviourally (a spy asserts a single delegation with the unwrapped objects and result identity), not only by AST. **Reconciliation Engine V1 is byte-identical** and still knows nothing about account identities; what changed is that an outer layer can now guarantee the precondition ADR-005 Decision 10 left external.

**`CrossAccountReconciliationError` is its own exception, not a reuse of `ReconciliationPreconditionError`.** The latter describes an input that is structurally irreconcilable *within one account* and is raised by the reconciler about the data it was given. A cross-account call is a caller wiring error — earlier, and about routing rather than data. The remedies differ (re-read the snapshot vs. fix who calls with what), and a caller catching a single exception type for both could not tell them apart. Neither is a subclass of the other, and this is asserted by test.

**Position ownership is unchanged.** Remote positions remain account-level, identified by `(symbol, side)`. No `bot_id` was added to any identity, wrapper, or position contract, and none is embedded in the order id's text. Per-bot attribution will live in the future Execution Ledger as a separate dimension (ADR-007, ADR-008).

## 16. Execution Ledger Event Contracts V1 (Hito 3.83 — ACCEPTED)

Pure contracts implementing the logical event model ADR-010 (Hito 3.82) already froze. **ACCEPTED** after a final independent adversarial re-audit (own probe harness, 73/73 passing, run before reading the new tests; own line-based mutation battery reinjected independently across all five event types, 5/5 detected; N36 reconfirmed equivalent with direct empirical proof; chain of custody verified by git tree-hash identity of `platform/`, not file-by-file) confirmed `ACEPTAR HITO 3.83` with zero BLOQUEANTE/IMPORTANTE findings — see `docs/progress.md` for the full re-audit record. No storage, no Projection Engine, no Repair, no write-side integration — `bybit_gateway.py` invokes no ledger and was not modified. This V1 covers only the submission lifecycle for a single order (`OrderSubmissionAttempted` → `OrderSubmissionOutcomeUnknown` / `OrderAcceptedByExchange` / `OrderRejectedByExchange` / `OrderObservedOpen`); it does **not** cover fills, cancel, amend, orphan observed orders, or persistence of any kind — none of those primitives exist yet. An independent adversarial audit had earlier classified `CORREGIR HITO 3.83` on a coverage-only finding — production was confirmed correct — and the correction closed it without touching any production file; see the note on `execution_order_id` type-safety coverage below.

**MENOR-1, registered without reopening 3.83 (found during the final re-audit).** The pytest node IDs for the `object()` case in `TestExecutionOrderIdTypeSafetyAcrossAllEventTypes` are derived from `repr(object())`, which embeds a memory address and therefore changes between runs — confirmed by collecting the same parametrized test twice. This affects readability, `--last-failed`, node-ID selection, and CI-run comparison for 5 of the 40 tests added in the post-audit correction. It does **not** affect behavior, coverage, or mutation detection — the same 5/5 mutations are caught regardless. Not fixed in this closure; a one-character `ids=` fix (a literal `"object"` label) would resolve it whenever the file is next touched.

**`ExecutionBotId` — optional bot identity, closing ADR-010's escalated OQ1.** The project director chose Option A (2026-08-27): a local opaque type structurally identical to `ExecutionAccountId` — received, never self-generated, no canonical format frozen (no external boundary to cross, same reasoning that left `ExecutionAccountId`'s format open). Optional on `OrderSubmissionAttempted`'s payload: its absence never means "unknown bot," it means "this event does not declare bot ownership" (e.g. a future Dashboard-triggered, non-bot flow).

**`ExecutionLedgerEventId` — the ledger fact's own identity.** Received, no generator, no frozen format — same treatment as `ExecutionAccountId`, for the same reason: this identifier never crosses the Bybit boundary, so there is no external constraint to derive a format from. It is not an idempotency key (ADR-010 Decision 7): it identifies the *record* of a fact, not the real-world fact itself.

**Authority is structural, not configurable.** Three non-instantiable marker classes — `LocalFact`, `RemoteFact`, `ObservedFact` — sit between `ExecutionLedgerEventPayload` and the five concrete event types, exactly mirroring `Divergence`'s marker pattern (ADR-005 Decision 7). No payload class exposes an `authority` field; which authority a fact carries is fixed by its Python type at class-definition time, never by a constructor argument — it is structurally impossible to construct, say, a LOCAL fact that later claims to be REMOTE.

**Five V1 event types, exactly what ADR-010 Decision 12 specified:**
- `OrderSubmissionAttempted` (LOCAL) — intent and attempt collapsed into one fact, recorded before any remote call; carries the full order intent (`symbol`/`side`/`order_type`/`quantity`/`price`, mirroring `ExecutionRequest`'s own LIMIT/MARKET price coupling) plus optional `execution_bot_id`.
- `OrderSubmissionOutcomeUnknown` (LOCAL) — the attempt ended without Phoenix being able to assert accept or reject; carries a closed four-value `reason` (`transport_failure` / `malformed_response` / `ambiguous_business_response` / `identity_mismatch`), never an exception object or a raw stack trace, never a repair decision.
- `OrderAcceptedByExchange` (REMOTE) — `execution_order_id` and `exchange_order_id` as two separate mandatory fields, never interchangeable, never a fallback of one for the other; plus `server_time_ms`.
- `OrderRejectedByExchange` (REMOTE) — `ret_code`/`ret_msg` as reported by the exchange (already-safe domain data, no headers/signatures/raw body) plus `server_time_ms`; never used for timeout, transport failure, or malformed response — those are `OrderSubmissionOutcomeUnknown`.
- `OrderObservedOpen` (OBSERVED) — see the dedicated note below on its V1 scope.

**`server_time_ms` closes a debt ADR-007/ADR-009 left open, with no new invention.** It is present on every REMOTE/OBSERVED payload and carries exactly the meaning already established and verified in ADR-010 F4: the same `BybitResponse.time_ms` field that already feeds `server_time_ms` in all four read-side interpreters — not an order-creation timestamp, the Bybit gateway's response-generation time.

**`OrderObservedOpen` V1 represents exclusively the correlated case — resolving ADR-010's OQ6, surfaced during this hito's implementation.** ADR-010 Decision 12 only described an open order that correlates to a Phoenix `ExecutionOrderId` (`order_id == orderLinkId`); it said nothing about an orphan (`order_id is None` on `ExecutionOpenOrder`) — the same case Reconciliation V1 already models as `UnattributedExchangeOpenOrder`. The project director froze the V1 semantics (2026-08-29): `execution_order_id` and `exchange_order_id` are both mandatory, non-Optional; constructing this event with `execution_order_id=None` raises `TypeError`; inventing a fake `ExecutionOrderId` or falling back to `exchange_order_id` as a stand-in Phoenix identity is explicitly forbidden and covered by dedicated tests. Orphan open orders remain observable exclusively through Reconciliation V1. **No sixth event type was added for the orphan case in 3.83** — that remains an explicit architectural debt for a future hito, before any Reconciliation → Ledger integration; it does not mean orphans will never be ledger-worthy, only that their representation is not designed yet.

**Envelope: four fields, none copied from any illustrative example.** `event_id` (`ExecutionLedgerEventId`), `execution_account_id` (`ExecutionAccountId`, universal — every account must be filterable/auditable without depending on future storage topology), `occurred_at_ms` (the producer's own local instant, received, never read from a clock inside the contract — reusing the same `MillisecondClock` Protocol already established, which was never HMAC-specific to begin with), and `payload`. Deliberately **no `sequence` field**: timestamp does not guarantee total order (two facts may legitimately share `occurred_at_ms`, protected by dedicated tests), and the physical assignment mechanism depends on a persistence technology this hito does not choose — it is a requirement the storage layer must satisfy later, not a field frozen now. Deliberately **no `ExecutionOrderId` on the envelope**: not every event has an order, so it lives in each type's own payload, matching the established "no near-always-empty optional fields" convention (ADR-004, ADR-005).

**No economic deduplication, anywhere.** Two `OrderSubmissionAttempted` facts with identical `symbol`/`side`/`order_type`/`quantity`/`price` but different `execution_order_id` are, and must remain, distinct facts — protected by test and by an independently-reinjected mutation that made equality ignore `execution_order_id`.

**Mutation battery: 24 specified (28 counting sub-mutations for `eq`-based variants), 28/28 detected, 0 survivors, 0 equivalents.** Five mutations survived on the first pass — `exchange_order_id` silently backfilling a missing `execution_order_id` on `OrderAcceptedByExchange`; `OrderSubmissionAttempted` equality ignoring `execution_order_id` (economic dedup); `ExecutionLedgerEvent` equality collapsing on shared `occurred_at_ms`; `execution_bot_id` contaminating another field (`symbol`) on construction; and `OrderRejectedByExchange` silently accepting a transport-failure reason as a valid business rejection. All five were genuine coverage gaps, not equivalent mutants: each was closed with a dedicated behavioral test (missing-ID rejection, value-equality-when-equal, exact field-set enumeration per event type, cross-field isolation) before re-confirming 28/28.

**Protected areas verified byte-identical:** `reconciliation_engine.py`, `reconciliation_contracts.py`, `account_scoped_reconciliation.py`, `expected_execution_state_contracts.py`, `exchange_state_contracts.py`, `execution_identity_contracts.py`, `execution_order_id_factory.py`, `contracts.py`, `bybit_gateway.py`, `bybit_api_error.py`, `bybit_create_order_response_interpreter.py`, all of `phoenix_core` (tree hash identical), `railway.toml`, `pyproject.toml`. `__init__.py` extended additively only.

**Post-audit correction — coverage-only, zero production changes.** An independent adversarial audit confirmed production correct in all five event types (manually verified against `None`, a bare string, `int`, `bool`, `float`, `bytes`, and `object()` as `execution_order_id`) but found that `OrderSubmissionOutcomeUnknown` and `OrderRejectedByExchange` carried **zero test coverage** proving `execution_order_id` must be exactly an `ExecutionOrderId` — a mutation that removed that check on `OrderSubmissionOutcomeUnknown` survived undetected. Only `OrderSubmissionAttempted` and `OrderObservedOpen` had this coverage; `OrderAcceptedByExchange` covered only the `None` case. `execution_ledger_event_contracts.py` itself was **not touched** — the finding was confirmed behaviorally before any test was written. `TestExecutionOrderIdTypeSafetyAcrossAllEventTypes` now covers all five event types symmetrically, parametrized by `(event_name, bad_value)` so a failure never hides which class regressed: 7 rejected values × 5 event types (35 rejections) plus 5 acceptance-by-identity checks. The N32-family mutation (removing the `isinstance` check) was independently reinjected against all five classes — 5/5 detected, including the exact mutation the audit found surviving and its analogue on `OrderRejectedByExchange`. The N36 mutation (syntactic `=None` defaults added to every `OrderObservedOpen` field) was reinjected once more and **still survives** — reconfirmed **equivalent** with the same empirical proof as the audit: `__post_init__` validates every field regardless of whether it carries a default, so the mutation changes only the constructor's signature, never observable behavior; no syntactic-only test was written to "kill" it, per explicit instruction. 40 new tests, suite 6149→6189.

## 17. Execution Ledger Writer / Durability Boundary (Hito 3.84 — DESIGN ONLY, STOP resolved: PostgreSQL, not implemented)

Design of the boundary that lets the accepted V1 events (§16) enter the real order path. Nothing here is implemented; `bybit_gateway.py`, `execution_ledger_event_contracts.py` and all of `platform/` are byte-identical to Hito 3.83's acceptance. Decisions and their evidence live in ADR-011; this section holds the two artifacts that are architecture rather than decision: the reconstructed failure windows of the current write path, and the failure matrix the Writer must be designed against.

### 17.1 The real write path and where it can fail

Everything before `urlopen` is pure local computation. Everything inside and after it may already have had a remote effect.

| Step | Component | Remote effect possible? | What can go wrong here |
|---|---|---|---|
| 1 | `ExecutionRequest.__post_init__` | No | Local validation `ValueError` — no order exists yet, **not ledger-worthy** (ADR-010 D15) |
| 2 | `BybitExecutionGateway._to_bybit_request` | No | `ExecutionRequestNotSupportedError` (`len(order_id)>36`, non-finite decimal) — pre-transmission adaptation, **not ledger-worthy** |
| 3 | `BybitDemoClient.place_order` → `BybitCreateOrderOperation.execute` → `payload_builder.build` | No | Pure; programming defects propagate as-is |
| 4 | `BybitEndpointExecutor` → `BybitPrivateApi` → `BybitPrivateRequestSender` → `request_builder.build` (HMAC, headers) | No | **Point A — last safe point.** Signing needs `MillisecondClock` and credentials; failure here is local |
| 5 | `UrllibHttpTransport.post` → `urllib.request.urlopen(...)` | **Yes** | **Point B — first point where transmission may have occurred**, invisible to Phoenix. DNS / refused / connect-timeout (not sent) vs. response-timeout / reset-after-send (sent) — **empirically indistinguishable from the exception alone** (ADR-011 F2) |
| 6 | `response.read()` / `.decode("utf-8")` | Already happened | `UnicodeDecodeError` → `BybitResponseProcessingError`; the order was received remotely |
| 7 | `BybitResponseParser.parse` | Already happened | Malformed JSON/schema → `BybitResponseProcessingError` |
| 8 | `BybitCreateOrderResponseInterpreter.interpret` | Already happened | `ret_code != 0` → `BybitApiError`; missing `orderId`/`orderLinkId` → `BybitResponseProcessingError` |
| 9 | `BybitExecutionGateway._to_execution_result` | Already happened | `orderLinkId` mismatch → `ExecutionInfrastructureError` **after a successful remote ACK — the order exists at Bybit** |
| 10 | `ExecutionResult` returned to caller | Already happened | Process may die between step 9 and the caller persisting anything |

Today, steps 5–9 all collapse into `ExecutionInfrastructureError("Bybit execution infrastructure failure")` — a single constant message — except business rejections (`ret_code ∈ {10001, 110003, 110004, 110007}`) which become `ExecutionResult(status="rejected")`. `ret_code 110072` ("OrderLinkedID is duplicate", verified against Bybit's official error page) is **not** in the rejection set and is therefore misclassified as infrastructure today, when it is the strongest available evidence that a prior attempt was accepted.

### 17.2 Failure matrix the Writer must satisfy

Assumes ADR-011 D6 (Attempted durable before `urlopen`) and D11 (post-remote append failure → account HALTED). "Knows" means what a correctly designed ledger can assert from its own records; "must not" is the action that would create a duplicate order or hide a real one.

| # | Scenario | What Phoenix knows | What Phoenix does NOT know | Events present | Can infer? | Forbidden action | Needs |
|---|---|---|---|---|---|---|---|
| F1 | Cannot persist `Attempted` | Nothing was transmitted (D6 blocks `urlopen`) | — | none | Safe: order never existed | Calling the inner gateway anyway | Nothing remote; caller sees `LedgerAppendError` |
| F2 | `Attempted` durable → process dies before network | An attempt was recorded | Whether `urlopen` ever ran | `Attempted` | **No** — indistinguishable from F3 from the ledger alone | Assuming not-sent; re-submitting with a *new* `ExecutionOrderId` | Recovery D10: read-side query by `orderLinkId` |
| F3 | `Attempted` durable → network starts → process dies | Same as F2 | Whether Bybit received/accepted | `Attempted` | **No** | Same as F2 | Same as F2 |
| F4 | `Attempted` durable → timeout, outcome unknown | Transport failed synchronously | Whether the order reached Bybit (empirically: often **yes**, ADR-011 F2 case D) | `Attempted`, `Unknown(transport_failure)` | No | Treating as rejected or as not-sent; retrying with a new id | Recovery D10, or immediate retry with the **same** `orderLinkId` (D9) expecting either ACK or `110072` |
| F5 | `Attempted` → Bybit accepts → process dies before persisting `Accepted` | An attempt was recorded | That it was accepted; `exchange_order_id` | `Attempted` | No — looks exactly like F2/F3 | Assuming not-sent | Recovery D10 → `OrderObservedOpen` (LIMIT still open) or **no V1 event exists** (MARKET filled — OQ2) |
| F6 | `Attempted` → Bybit rejects → process dies before persisting `Rejected` | An attempt was recorded | That it was rejected | `Attempted` | No | Assuming not-sent | Recovery D10; query returns not-found → escalate, do **not** auto-resubmit |
| F7 | `Accepted` received → append fails | Order **exists** at Bybit, `exchange_order_id` in memory | Whether the ledger will ever accept the write | `Attempted` only | Yes — the process still holds the fact | Continuing to submit for this account; discarding the in-memory fact silently | D11: bounded retry → emergency log line → account **HALTED** → recovery |
| F8 | `Rejected` received → append fails | Order was refused | Same as F7 | `Attempted` only | Yes | Same as F7 | D11 identical; recovery cost is one wasted query, **no duplicate risk** (id not reused) |
| F9 | Ledger store temporarily unavailable | Nothing can be made durable | — | whatever existed | Safe by construction | Any submission (D6 blocks it) | Wait / HALTED; this is why the WAL must not sit behind a network hop (ADR-011 D1, STOP Option B risk) |
| F10 | Restart with `Attempted` lacking any terminal | The attempt exists | Which of F2/F3/F5/F6 happened | `Attempted` (± `Unknown`) | **No** — this is the union of all crash windows | Inferring anything from absence | Recovery D10, read primitive OQ3, closed-order event OQ2 |

Two structural conclusions fall out of the matrix. First, F2/F3/F5/F6/F10 are **the same state from the ledger's point of view** — "Attempted without terminal" — which is why recovery must query, never infer. Second, the only scenarios that are safe *by construction* are F1 and F9, and both are safe **only because** the Writer sits before `urlopen` and refuses to let the inner gateway run without a receipt; move the ledger write after the network call and every row of this table becomes a duplicate-order hazard.

### 17.3 What the boundary is, and is not

- **Is:** a write-ahead intent log for the remote call, an idempotent remote key (`orderLinkId` = `ExecutionOrderId`, duplicate → `110072`), and a read-side-driven recovery loop. Consistency between ledger and exchange is *eventual and named* — the "Attempted without terminal" and `Unknown` states are its honest representation.
- **Is not:** a transactional outbox (Phoenix transmits synchronously; a relay would add exactly the double-state window being avoided), a saga (there is no compensation — an order cannot be un-sent, and no cancel primitive exists), or an atomic commit across ledger and Bybit (impossible; not pretended).
- **Authority:** a Port-level wrapper around any `ExecutionGateway`, wired by the composition root so the inner adapter is never reachable except through it — the same "wrap without rewriting" pattern accepted for account scoping in Hito 3.81. `BybitExecutionGateway` gains no hook, callback, or ledger parameter.
- **Single logical writer per `ExecutionAccountId`** (ADR-011 D12). With the STOP resolved toward PostgreSQL, this is **not** platform-enforced — Phoenix must impose it itself (per-account advisory lock in the append transaction).

### 17.4 Open before implementation (see ADR-011)

OQ1 `orderLinkId` uniqueness window at Bybit (undocumented) · ~~OQ2 no V1 event for an order observed **closed**~~ — **designed in Hito 3.85 as `OrderObservedClosed`, see §18 and ADR-012** · OQ3 read primitive — **scope grew in 3.85**: `realtime`'s closed-order cache is volatile per official docs, so recovery needs a new primitive on `/v5/order/history`, not a `realtime` tweak · OQ4 `110072` recognition · OQ5 retry/HALTED parameters · OQ6 volume backup cadence · OQ7 bot placement under account serialization. **STOP — resolved 2026-09-11 by the project director: Option B, managed PostgreSQL on Railway** (against the recorded Option A recommendation; ADR-011 keeps both). Consequences now fixed: durable = PostgreSQL commit with `synchronous_commit=on`; F9 becomes a real network failure window — *if PostgreSQL is unreachable, Phoenix places no orders* (fail-closed by D6, expected behavior, not an incident); **single-writer-per-account is no longer platform-enforced and must be imposed by Phoenix** (per-account `pg_advisory_xact_lock` inside the append transaction, which also assigns `sequence`); immutability via `REVOKE UPDATE, DELETE` on the Writer role; `pyproject.toml` gains its first `dependencies` entry (driver choice deferred to the implementation hito); connection URL loaded fail-closed from environment and never logged. Not implemented in 3.84.

## 18. Closed Order Observation (Hito 3.85 — ACCEPTED, design only, not implemented)

Closes the gap ADR-011 OQ2 left open: the accepted V1 events (§16) cannot represent an order found **closed** by the read-side, so the single most dangerous story in the system — a MARKET order filled during a lost response — could never be closed in the ledger. ADR-012 designs the missing event; nothing is implemented, and `execution_ledger_event_contracts.py` is byte-identical.

**One event, not three.** `OrderObservedClosed` (authority `ObservedFact`, consistent with `OrderObservedOpen`) carries `remote_status ∈ {filled, cancelled, rejected}` as a closed, cross-validated set — the same pattern as `OrderSubmissionOutcomeUnknown.reason`. Per-status types were rejected because a Projection treats all three identically (terminal, absorbing, apply `filled_quantity`) and because a LIMIT order partially executed then cancelled is *both* things at once: a type named "Cancelled" would hide the execution, one named "Filled" would lie. Bybit's own docs settle the point: "In derivatives, orders with this status [Cancelled] may have an executed qty." `Deactivated`, `PartiallyFilledCanceled` (spot-only) and `Triggered` (transitional, already treated as open since 3.71) are structurally impossible for a Phoenix linear market/limit order and fail closed at the interpreter.

**Authority is OBSERVED, not REMOTE — and this is not an inconsistency with 3.83.** REMOTE is Bybit's *synchronous* answer to Phoenix's *own* submission, where Phoenix witnessed the causal chain; OBSERVED is Bybit state discovered later and correlated by identity. Both originate at the exchange; what differs is the causal testimony. A `Rejected` found by GET therefore becomes `OrderObservedClosed(remote_status="rejected")`, never a retroactive `OrderRejectedByExchange` — that would fabricate a `ret_code` Phoenix never received.

**"Filled" is not a fill ledger.** `filled_quantity` / `filled_value` / `average_price` are Bybit's **order-level cumulative aggregates** (`cumExecQty` / `cumExecValue` / `avgPrice`), carried as attributes of the order. Phoenix asserts nothing about individual executions, per-fill fees (`cumExecFee` is deprecated for linear — rejected), maker/taker, or trade attribution. `leaves_qty` is rejected as derivable. Four timestamps, none of them called "fill time": `occurred_at_ms` (envelope), `server_time_ms` (the GET's `time_ms`, as everywhere in the read-side), `remote_created_time_ms` and `remote_updated_time_ms` (Bybit's `createdTime`/`updatedTime`, named for what Bybit documents them as and nothing more).

**Idempotency — a prospective refinement of ADR-011 D5.** A closed order is terminal and therefore **content-stable**, so `UNIQUE (account, order_id, event_type)` is correct for `OrderObservedClosed` (unlike `OrderObservedOpen`, which legitimately repeats). New rule: a key collision with *different* content is an integrity failure that fails closed and escalates — never a silent overwrite, never a silent "return existing receipt."

**Corrected after the final re-audit (2026-09-17) — what "content" means.** The re-audit found the one IMPORTANTE of 3.85: D12 said two observations of the same closed order "must be identical" and ordered fail-closed on "different content" without defining it — yet `server_time_ms` (the GET's response time, required by D7/D8) differs on **every** legitimate re-observation, so a naive full-payload comparison would raise a false integrity error on the exact flow the STOP resolution enables (`realtime` fast-path then `history`, or recovery run twice). ADR-012 now splits the 17 D16 fields exhaustively: **16 STABLE REMOTE FACT CONTENT** fields (`execution_order_id`, `exchange_order_id`, `symbol`, `side`, `order_type`, `quantity`, `filled_quantity`, `filled_value`, `remote_status`, `reduce_only`, `remote_created_time_ms`, `remote_updated_time_ms`, `price`, `average_price`, `cancel_type`, `reject_reason`) and **1 OBSERVATION METADATA** field (`server_time_ms`). On key collision the Writer compares only the 16: all equal → idempotent success, no second event, no error, **first durable observation wins** for `server_time_ms` (existing event never mutated); any of the 16 differs → integrity error, fail-closed, escalate, never overwrite. The `UNIQUE` itself is unchanged. Two MENORES deferred to the interpreter hito (undocumented `cancelType` sentinel for non-cancelled orders; conservative `cancelled ⇒ filled_quantity < quantity`), and one pre-existing ADR-011 debt recorded for the Writer hito (repeated legitimate `Unknown` under D9 retries would collapse under D5's key). **A second, independent final re-audit focused exclusively on this correction — a Writer implemented from reading only the correction text, never the implementer's own account, cleared 21/21 probes including four real collisions and a 10/10 blind-reentry test — found zero BLOQUEANTE/IMPORTANTE findings: `ACEPTAR HITO 3.85`.** Production still untouched; the design is accepted, not implemented.

**Ledger stories this makes representable** (append-only; `Unknown` is never rewritten, the Projection derives current state from the latest terminal fact): `[Attempted, Unknown, ObservedClosed]` (lost response, the acceptance case) · `[Attempted, ObservedClosed]` (crash window — no retroactive `Unknown` is invented; the gap *is* the evidence) · `[Attempted, Accepted, ObservedClosed]` (the ordinary lifecycle — the event carries no recovery/error semantics) · `[Attempted, Unknown(110072 path), ObservedClosed]` (duplicate `orderLinkId` → lookup → the single order Bybit kept).

**The STOP.** Official docs state that `realtime`'s closed-order cache "clears and accumulates again" when Bybit restarts — it is not a durable source. The durable source is `/v5/order/history`, which Phoenix does not implement, with **asymmetric retention**: 24 h for zero-fill cancellations, rejections and deactivations; 7 days for other closed states; beyond 7 days only orders with fills. The dangerous case (capital moved) is the longest-retained; the inert case expires first. Accepting a new read primitive on a new endpoint, and accepting "down > 24 h ⇒ inert orders become unresolvable and are escalated, never retried" as the recovery horizon, are scope and risk decisions — recommended (Option A), not taken.

**Resolved 2026-09-14 by the project director: Option A.** `/v5/order/history` is the durable, authoritative recovery source; `realtime` (`openOnly=1`) may later serve as a fast-path but recovery correctness must never depend on its cache. If `history` finds the order, the matching OBSERVED fact is recorded; if it does not, Phoenix is **forbidden** to infer that Bybit never received it, that it was rejected, or that resubmission is safe — unresolved `Attempted`/`Unknown` past the operational horizon escalates fail-closed, never auto-resubmits. The `>24 h` horizon is an **operational, configurable policy**, explicitly *not* an exchange guarantee: the 24 h / 7 d / fills-only figures in ADR-012 F5 are the endpoint's documented *retention* (an upper bound the policy must not exceed), not an ontological claim about the order. Durable evidence source and resolution-time policy are kept as two separate concerns. ADR-011 D10 step 2 is prospectively superseded (`history`, not `realtime`); ADR-011 OQ3 is redefined as a lookup primitive on `/v5/order/history`. **Hito 3.85 is accepted (see above); the endpoint itself is not implemented.** Next hito (3.86): implement and audit the read-side `orderLinkId` lookup on `/v5/order/history`.

## 19. Order History Lookup by orderLinkId (Hito 3.86 — ACCEPTED)

Implements the durable recovery-source read primitive ADR-012's STOP resolution required: an isolated lookup of `GET /v5/order/history` by `orderLinkId`, correlated to a Phoenix `ExecutionOrderId`. Read-side only — no recovery worker, no `OrderObservedClosed`, no Ledger append, no PostgreSQL, no `110072` handling, no resubmission, no `realtime` fast-path/fallback. `bybit_gateway.py`, `execution_ledger_event_contracts.py`, and every other production file are untouched; only `bybit_endpoints.py` (new endpoint constant) and `__init__.py` (exports) were extended additively.

**Explicit FOUND/NOT_FOUND contract, never `None`.** Same marker-class pattern as `Divergence`/`LocalFact`-`RemoteFact`-`ObservedFact`. `BybitOrderHistoryOrderNotFound`'s docstring states precisely what it does **not** mean — not never-sent, not rejected, not safe-to-resubmit — matching ADR-012's Resolution of the STOP verbatim. **Cardinality: 0 → NOT_FOUND, 1 → FOUND, >1 → fail closed.** Never picks an arbitrary first match. Pagination: any non-empty `nextPageCursor` fails closed — official docs do not guarantee it stays empty for an exact `orderLinkId` filter, so the primitive never follows a cursor loop or serves a possibly-incomplete result.

## 20. Duplicate ExecutionOrderId / Bybit `110072` Semantics (Hito 3.87 — DESIGN ONLY, STOP resolved: Option B, not implemented)

Resolves the *meaning* of `retCode 110072` ("OrderLinkedID is duplicate") that ADR-011 OQ4 left open, without implementing anything. Decisions and evidence live in ADR-013; this section holds the architectural consequences.

**What `110072` is, and is not.** It is two REMOTE facts that must never be fused: the *second request* was rejected because identity X is already taken, and Bybit thereby asserts that an order with `orderLinkId = X` exists or existed within an undocumented uniqueness scope. It is **not** a terminal fact about order X: not a rejection of X (the order may be `Filled`), not an acceptance of X as intended (economics unverified, and `OrderAcceptedByExchange` structurally requires an `exchange_order_id` that `110072` does not supply), not a licence to resubmit under X or under a fresh id. Today `bybit_gateway.py` already excludes `110072` from `_ORDER_REJECTION_RET_CODES` by design; ADR-013 D3 elevates that to a model rule — `ret_code=110072` is a prohibited value for `OrderRejectedByExchange`.

**Frozen action rule (ADR-013 D6).** After `110072`: no further create-order with X; no fresh `ExecutionOrderId` for the same intent while X is unresolved; mandatory resolution by reading, open orders first (`/v5/order/realtime` by `orderLinkId`), then closed orders (`/v5/order/history`, Hito 3.86); no negative result is ever conclusive; every positive result must pass **economic verification** against `OrderSubmissionAttempted(X)` — `symbol`, `side`, `order_type`, `quantity` (exact `Decimal`), `price` (exact for `limit`, both `None` for `market`), `reduce_only` (`False`) — before any observation is appended. A mismatch is an integrity failure: account HALTED (ADR-011 D11), escalation, no append, no resend. `110072` followed by NOT_FOUND on both sources is *unresolved identity* — same HALTED/escalation path, never an inference of "not sent".

**Open orders need `realtime` — this is a fact, not a re-litigation of ADR-012.** `/v5/order/history` is documented closed-only; Phoenix has no WebSocket; therefore `/v5/order/realtime` (`openOnly=0`, the mode already accepted in Hito 3.71) is the *only* REST source for a still-open X, and its cache-volatility concern (which motivated ADR-012's STOP) applies to the closed-order cache, not to live open state. ADR-012's resolution — `history` durable for closed orders, `realtime` never sole source for closed — stays intact; ADR-013 D7 fills the case it did not cover. Consequence: a `realtime` lookup-by-`orderLinkId` primitive (sibling of 3.86's) is a prerequisite that does not exist yet.

**The STOP.** `110072` is ledger-worthy (audit, deterministic replay, crash-safety between receiving it and resolving it), but every representation touches a director-reserved decision: **A** — no new fact, keep it as `Unknown(ambiguous_business_response)` (loses the evidence; a second `Unknown(X)` would also collide with the Writer's idempotency key and be silently dropped); **B** — a new REMOTE, *non-terminal* event `OrderIdentityReportedDuplicateByExchange` with `execution_order_id`/`ret_code`/`ret_msg`/`server_time_ms` (semantically exact, idempotency-clean, but a seventh event type and the first non-terminal REMOTE fact); **C** — `OrderRejectedByExchange` with a special classification (rejected: false terminal state); **D** — a new `Unknown` reason `duplicate_identity_reported` (wrong authority — LOCAL for a REMOTE assertion — and blocked by the known repeated-`Unknown` idempotency debt). **Recommended: B.** Escalated, not taken.

**Resolved 2026-09-21 by the project director: Option B.** A seventh event type, `OrderIdentityReportedDuplicateByExchange` (`RemoteFact`), will carry `execution_order_id`, `ret_code` (invariant: exactly `110072` in V1), `ret_msg`, `server_time_ms` — no `exchange_order_id` (structurally absent from a `110072` response), no economics (they live in `Attempted(X)`), no inheritance from `OrderRejectedByExchange`. It is the model's first **non-terminal REMOTE fact**: the Projection must treat it as evidence that never closes X, coexisting with a prior `Unknown(X)` and with the later observation. Idempotency: own content key `(account, X, type)` with `ret_code`/`ret_msg` as stable content and `server_time_ms` as observation metadata. `bybit_gateway.py`'s rejection set does not change; the future Port wrapper recognizes `110072` and appends this event instead of `Unknown(ambiguous_business_response)`. Not implemented — the contract extension, Projection rule, wrapper recognition, and the `realtime` lookup primitive are separate future hitos.

**Debts and prerequisites recorded, none resolved:** `orderLinkId` uniqueness scope/window — undocumented, needs empirical Bybit Demo verification (ADR-013 OQ1); operational distinction between `110072`/`110014`/`110030` under fast retries (OQ2); how the ADR-011 D6 wrapper recognizes `110072` (OQ3); the `realtime` lookup primitive (OQ4); the economic comparator (OQ5). The repeated-`Unknown` Writer debt (ADR-012) becomes blocking only if the STOP resolves toward Option D.

## 21. Order Realtime Lookup by orderLinkId (Hito 3.88 — ACCEPTED)

**Decisive finding, re-verified against current official docs (not inferred from `history`): `openOnly` is ignored when filtering by `orderId`/`orderLinkId`.** A correlated identity query can legitimately return a *closed* row — this is not a hypothetical edge case, it is documented Bybit behavior. - **`BybitRealtimeOrderFoundOpen`** — a new contract, same 16-field vocabulary as ADR-012 D16 (minus `cancel_type`, which has no field at all here — an order that is open was, by definition, never cancelled) — with its own invariants: `remote_status ∈ {new, partially_filled}`, `filled_quantity` strictly `< quantity` (a full fill is `Filled`, not open), the same `average_price`/`filled_value` zero-iff-zero coupling as the closed contract.
